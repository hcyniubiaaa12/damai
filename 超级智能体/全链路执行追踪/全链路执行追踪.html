每轮对话生成一个 traceId， 贯穿 编排决策 → 检索过程 → 证据评估 → 模型调用 → 工具调用 → 收尾归档。 本项目的"全链路追踪"不用 @Aspect 切面， 而是用手工 span（每个业务方法自己 startStage/completeStage） 换取能写入高度业务化的 snapshot； 扩展点靠 Spring 自动注入的 SPI 接口； 编排靠 顺序编排 pipeline + 策略注册表分派（非经典责任链，见第 4 节澄清）。

01 · CONCEPT MAPPING

三种模式，分别落在哪里

把"全链路追踪"的表述拆成几种设计模式，再逐个对照到项目里的实现类。关键结论：不是经典 AOP 切面，也非经典责任链——用手工 span + pipeline + 策略注册表达到相近的解耦/扩展效果；因为 Reactor 响应式流里 @Around 难以捕获业务上下文。

表述概念实际实现为何这样选
AOP 执行追踪ConversationTraceRecorder 的 startStage / completeStage / failStage，每个业务方法手工埋点（手工 span 模式）通用切面拿不到"子问题数/引用数/通道追溯"这类业务字段；手工埋点能把任意对象塞进 snapshot JSON
插件扩展检索通道 SPI RetrievalChannel + 执行器接口 ConversationExecutor，Spring 自动注入 List<T>，注册到 EnumMap新增通道/执行器只需写一个 @Component，无需改调度代码——开闭原则
编排分派
（非经典责任链）		ChatPreparationOrchestrator#prepare 顺序编排 pipeline（MEMORY→REWRITE→ROUTE）+ ConversationExecutorRegistry#get(mode) 策略分派不是 Chain.doFilter() 那种"处理或传递"的责任链：prepare 是无条件顺序流水线，registry 是策略注册表选一个执行。常被类比为责任链，但形态不同
编排决策ChatPreparationOrchestrator + DocumentQuestionRouter + KnowledgeRouteService决定走 GRAPH_ONLY / GRAPH_THEN_EVIDENCE / RETRIEVAL / REACT_AGENT / CLARIFICATION 哪条路
检索过程RagRetrievalEngine：多通道并行 → RRF 融合 → 父块提升 → Rerank每个子问题 × 每个通道都落 channel_execution + retrieval_result 行
证据评估RagPromptAssemblyService（EVIDENCE_BUDGET 阶段）token 预算切分、引用裁剪，snapshot 记录渲染/省略的引用
模型调用ObservedChatModelService 包装 ChatModel，每次调用落 ChatModelUsageTrace记录 provider/model/token 数/估算成本/耗时/状态
工具调用ChatToolTrace + DashScopeCompatibilityInterceptor + TavilyToolInputFallbackInterceptor框架级 Model/Tool 拦截器链，记录入参/输出/引用数/耗时
端到端耗时TaskInfo.startTime 差值 + 各阶段 durationMs + StageBenchmarkService 滑动窗口 P50/P90/P99单次耗时落 exchange 表，聚合统计落 stage_benchmark 表
02 · TRACING SKELETON

追踪骨架：Recorder + Store

每轮对话在 BusinessChatService#createTaskInfo 里 new 一个 ConversationTraceRecorder，它是一张薄门面，背后是阶段持久化 ConversationTraceStageStore 和检索观测 RetrievalObserveStore。

ConversationTraceRecorder

chatagent/service/ConversationTraceRecorder.java

每轮对话的追踪上下文载体。持有 conversationId / exchangeId / traceId、线程安全的模型调用列表 modelUsageTraces、可变限流统计 limitStats。把阶段生命周期和检索观测的细节封装成最常用的几个方法——这就是"手工 span"的发起者。

04 · ORCHESTRATION & PLUGIN

编排决策（顺序编排 + 策略分派）+ 执行器（插件扩展）

准备阶段是一条顺序 pipeline（MEMORY→REWRITE→ROUTE 顺序执行），执行阶段是策略注册表按 ExecutionMode 选一个执行器。⚠️ 两者都不是经典责任链的"处理或传递"形态——prepare 里各步无条件顺序执行、不做"我处理不了就传给下一个"的判断；registry 是选一个执行而非沿链传递。只是解耦/可扩展的效果与责任链相近，故常被类比。

ChatPreparationOrchestrator — 编排决策引擎

chatagent/rag/service/ChatPreparationOrchestrator.java

顺序编排 pipeline 的核心。每步用 startStage → try{ completeStage } catch{ failStage; throw } 包裹——⚠️ 这层 try/catch 只是追踪埋点 + 异常兜底，跟"链"结构无关，套在 pipeline 或责任链上都行；失败会把异常类+堆栈注入 snapshot 后原样向上抛（不吞异常），保证阶段记录闭合又不改变业务语义。

10 · LIFECYCLE

一次对话的追踪生命周期

把前面所有零件串成一条真实数据流：从 createTaskInfo 建 recorder，到 finishSuccessfully 归档 debugTrace，再到管理后台查询。

// 1. 入口：建追踪上下文
BusinessChatService.createTaskInfo()
  ├─ traceId = UUID;  new ConversationTraceRecorder(store, observeStore, conv, exchange, traceId)
  └─ TaskInfo 持有 traceRecorder

// 2. 准备阶段（顺序 pipeline：MEMORY→REWRITE→ROUTE）
ChatPreparationOrchestrator.prepare(taskInfo)
  ├─ recorder.startStage(MEMORY)   → INSERT trace_stage (RUNNING)
  ├─ recorder.completeStage(MEMORY) → UPDATE (COMPLETED, durationMs, snapshot)
  ├─ recorder.startStage(REWRITE)  → ... completeStage
  └─ recorder.startStage(ROUTE)    → ... completeStage   // 决定 ExecutionMode

// 3. 执行阶段（策略注册表分发）
executorRegistry.get(mode).execute(taskInfo)   // RagChatExecutor 等
  ├─ recorder.startStage(RAG_RETRIEVE)
  │   └─ ragRetrievalEngine.retrieve()
  │       ├─ recorder.recordChannelExecutions() → batch INSERT channel_execution
  │       └─ recorder.recordRetrievalResults()  → batch INSERT retrieval_result
  ├─ recorder.completeStage(RAG_RETRIEVE)
  ├─ recorder.startStage(EVIDENCE_BUDGET) → ... completeStage
  └─ recorder.startStage(ANSWER_GENERATE)
      └─ observedChatModelService.streamText() → addModelUsageTrace()

// 4. 收尾归档
BusinessChatService.finishSuccessfully(taskInfo)
  ├─ recorder.startStage(RECOMMENDATION) → completeStage
  ├─ recorder.startStage(FINALIZE)       → completeStage
  ├─ conversationArchiveStore.completeExchange(... debugTrace ...)
  │   └─ UPDATE exchange SET debug_trace_json = ChatDebugTrace JSON
  └─ stageBenchmarkService.recordDuration(stageCode, mode, durationMs)

// 5. 管理后台查询
POST /api/chat/exchange/detail          → listStageViews()      // 全部阶段行
POST /api/chat/exchange/retrieval/results → listResults()      // 全部 chunk 行
POST /api/chat/stage/benchmarks        → listAll()            // P50/P90/P99
三个"维度数据"对应三张表：阶段链路 → trace_stage（编排/生成/收尾）；检索明细 → channel_execution + retrieval_result（检索过程）；调用与耗时 → exchange.debug_trace_json + stage_benchmark（模型/工具调用 + 端到端耗时）。这正是表述里"多维度数据"的物理落点。
