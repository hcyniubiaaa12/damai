一次对话写进数据库，
后台能把它原样读回来

路由决策、检索结果、证据评估、模型调用耗时——这些执行链路数据，不是日志文件里的字符串， 而是结构化地落进 5 张追踪表 + 1 个聚合 JSON 列。 管理后台通过 /api/chat/exchange/detail 等端点把它们原样读回，组装成 对话详情视图，供问题排查与问答质量持续优化。 写入靠 ConversationArchiveStore（归档）+ TraceStageStore / RetrievalObserveStore（链路）， 读取靠 BusinessChatService 的查询方法。

详情入口 · POST /api/chat/exchange/detail → getExchangeDetail(conversationId, exchangeId)
同一条链路的两个方向 写 = 归档 + 链路落库 · 读 = 详情视图组装

写入侧 · 落库

ConversationArchiveStore + TraceStageStore + RetrievalObserveStore

对话开始建 RUNNING 轮次；执行中每个阶段/通道/chunk 实时落表；结束时 completeExchange 把答案、引用、debugTrace、首 token / 总耗时一次性回写。

  • startExchange → 建 dialogue + exchange
  • startStage/finishStage → trace_stage 表
  • recordChannelExecutions → channel_execution 表
  • recordRetrievalResults → retrieval_result 表
  • completeExchange → exchange.debug_trace_json + latency

读取侧 · 后台查看

BusinessChatController + BusinessChatService

管理后台按会话/轮次拉数据：对话详情把 exchange（含 debugTrace）和全部阶段链路拼成一个视图；检索明细、通道执行、耗时基准各自独立端点。

  • /exchange/detail → 详情 + 阶段链路
  • /exchange/retrieval/results → 每 chunk 结果
  • /exchange/channel/executions → 每通道执行
  • /stage/benchmarks → P50/P90/P99
  • /session/detail · /session/list → 会话维度
01 · PERSIST

记录到数据库：什么数据，写到哪张表

执行链路的每一类数据都有对应落点。表名前的 写 标注触发写入的方法。关键是 completeExchange 一次性回写轮次终态——答案、引用、整段 debugTrace 序列化为 JSON、首 token 与总耗时。

链路数据落库表 / 列粒度触发写入
路由决策trace_stage（ROUTE 行 snapshot）+ knowledge_route_trace每阶段/每次路由startStage/finishStage(ROUTE) · KnowledgeRouteService.recordAutoRoute/recordShadowRoute
检索结果retrieval_result每 chunkRagRetrievalEngine.recordRetrievalResultObservations → recordRetrievalResults
检索通道执行channel_execution每子问题×通道RagRetrievalEngine.recordChannelObservations → recordChannelExecutions
证据评估trace_stage（EVIDENCE_BUDGET 行 snapshot）每阶段startStage/finishStage(EVIDENCE_BUDGET)，snapshot 含预算/渲染省略引用
模型调用耗时exchange.debug_trace_json（modelUsageTraces）每次调用ObservedChatModelService → addModelUsageTrace → 归档时序列化
工具调用exchange.debug_trace_json（toolTraces）每次调用ReAct 执行器收集 ChatToolTrace
端到端耗时exchange.first_token_latency_ms / total_latency_ms + stage_benchmark每轮 + 每 stagecompleteExchange(firstResponseTimeMs,totalResponseTimeMs) · StageBenchmarkService.recordDuration
整轮聚合exchange.debug_trace_json（ChatDebugTrace）每轮completeExchange(..., ChatDebugTrace debugTrace, ...)

ConversationArchiveStore — 归档存储（轮次终态写入）

chatagent/service/ConversationArchiveStore.java · MybatisConversationArchiveStore.java

对话生命周期的持久化总管。开始时建会话+轮次，结束时把整轮结果（含 debugTrace JSON、latency）一次性回写。

方法签名职责
ConversationExchangeView startExchange(conversationId, question, chatMode, selectedDocumentId, selectedDocumentName)upsert dialogue + INSERT exchange（RUNNING 状态），返回轮次视图
void refreshSessionScope(conversationId, chatMode, docId, docName)刷新会话作用域（模式 / 选中文档）
void completeExchange(conversationId, exchangeId, answer, thinkingSteps, references, recommendations, usedTools, debugTrace, status, errorMessage, firstResponseTimeMs, totalResponseTimeMs)轮次终态一次性回写：答案/推理步/引用/推荐/工具/整段 debugTrace JSON/状态/错误/首 token 与总耗时，并把会话置 IDLE
Optional<ConversationArchiveRecord> getSessionRecord(conversationId)加载会话 + 全部轮次（详情视图用）
ConversationArchivePage listSessionRecordPage(pageNo, pageSize, keyword, chatMode, turnStatus)分页会话列表，支持关键词 / 模式 / 轮次状态过滤
ConversationRemovalResult deleteSession(conversationId)删会话 + 全部轮次（重置时调用）
关键设计：阶段/检索数据是实时逐条落表（即便对话中途失败也已落库，可排查）；而 ChatDebugTrace 是内存聚合、结束时一次性序列化进 debug_trace_json 列——两种策略并存：实时落表保排查，聚合 JSON 保回放。

ConversationExchangeDetailView — 对话详情视图

chatagent/model/ConversationExchangeDetailView.java

后台"对话详情"页直接消费的复合视图：把轮次本体和阶段链路拼到一起，前端可一次拉取整条执行过程。

字段类型来源 / 含义
conversationIdString会话标识
exchangeConversationExchangeView轮次本体：问题/答案/引用/推荐/工具/debugTrace/latency（来自 exchange 表）
stageTracesList<ConversationTraceStageView>该轮全部阶段链路，按 stageOrder 排序（来自 trace_stage 表）
组合点：一个视图同时跨 exchange 表（轮次终态 + debugTrace JSON）和 trace_stage 表（阶段明细）——这就是"每次对话的详细执行过程"在后台的物理形态。
03 · DETAIL ASSEMBLY

"查看对话详情"的完整调用链

从后台点击某轮对话，到屏幕上看到路由决策/检索/证据/生成全过程，数据是这样流回来的。

// 后台请求：POST /api/chat/exchange/detail  body: {conversationId, exchangeId}
BusinessChatController.exchange(dto)
  └─ BusinessChatService.getExchangeDetail(conversationId, exchangeId)

// 1) 取整会话（含全部轮次）
   conversationArchiveStore.getSessionRecord(conversationId)   // ← exchange 表 + dialogue 表
     → toSessionView(record, withDetail, withDetail)
     → overlayRuntimeSnapshot(sessionView)            // 叠加运行中轮次的实时快照

// 2) 从会话里按 exchangeId 定位该轮
   sessionView.getExchanges().stream()
     .filter(x -> x.getExchangeId() == resolvedExchangeId)
     .findFirst()                                          // ← exchangeView（含 debugTrace 反序列化）

// 3) 取该轮全部阶段链路
   conversationTraceStageStore.listStageViews(conversationId, exchangeId)   // ← trace_stage 表
     按 stageOrder → startTime → id 升序

// 4) 拼装详情视图返回
   return new ConversationExchangeDetailView(
       conversationId,
       exchangeView,        // 路由决策/证据/模型调用耗时/工具调用 → 都在 debugTrace 里
       stageTraces          // MEMORY/REWRITE/ROUTE/RAG_RETRIEVE/.../FINALIZE 每段状态+耗时+snapshot
   );

// 前端还可并行拉明细端点：
//   /exchange/retrieval/results   → 每 chunk 排名/分数/是否选中（retrieval_result 表）
//   /exchange/channel/executions  → 每通道召回/采纳/耗时（channel_execution 表）
视图分层：详情视图给"骨架"（轮次 + 阶段链路），检索明细端点给"血肉"（每 chunk / 每通道）。两者按 conversationId + exchangeId 关联——同一轮对话的多维度数据被同一对键串联起来。
04 · TROUBLESHOOT

问题排查：失败也能查到现场

链路数据是实时逐条落表的，所以即便对话中途异常，已落库的阶段记录依然完整——失败阶段还额外注入了异常类与堆栈。

失败现场的三重记录

排查维度落点怎么用
阶段级失败trace_stage 行 stage_state=FAILED + error_message + snapshot 内 exceptionClass / stackTrace定位是哪一段（ROUTE? RAG_RETRIEVE? ANSWER_GENERATE?）挂了；failStage(handle, ..., Throwable, snapshot) 自动注入堆栈
轮次级失败exchange 行 exchange_state=FAILED + finish_note（errorMessage）FINALIZE 阶段在 finishWithFailure 触发，整轮标失败但已归档
模型调用失败debugTrace.modelUsageTraces 里 status=FAILED 的记录看是哪个 provider/model 调用失败、token 消耗到哪一步
工具调用失败debugTrace.toolTraces 里 errorMessage 非空的记录看哪个工具（如 tavily_search）入参/执行失败
排查路径：先 /session/list 找到失败会话 → /session/detail 看哪轮 turnStatus=FAILED → /exchange/detail 看 stageTraces 哪段 FAILED + snapshot 里的 stackTrace → 必要时 /exchange/retrieval/results 看检索是否召回不足。一条链路顺藤摸瓜。
05 · OPTIMIZE

持续优化问答质量：用追踪数据反哺

落库的链路数据不只是给人看现场，更是质量优化的原料——路由准确性、检索召回质量、性能瓶颈三类分析各有专属数据。

三类质量分析的数据来源

优化方向数据来源分析方式
路由准确性super_agent_knowledge_route_trace 表：selectedDocumentId / hitSelectedDocument / confidenceDOCUMENT 模式记录影子路由（recordShadowRoute），事后比对"自动路由选的文档" vs "用户实际选的文档"（hitSelectedDocument），量化路由命中率
检索召回质量retrieval_result 表：gate_passed / is_elevated / is_selected / selection_reason + channel_execution 的 recalled_count / accepted_count看每个通道的召回→采纳→最终选中漏斗；original_score/rrf_score/rerank_score 对比定位是召回不足还是 rerank 没排对
性能瓶颈stage_benchmark 表：P50/P90/P99 + exchange.first_token_latency_ms / total_latency_msStageBenchmarkService 按 stage+mode 滑动窗口（≤200 样本）算百分位，定位哪个阶段 P99 飙高；首 token 延迟单独看流式体感
成本与 tokendebugTrace.modelUsageTraces：promptTokens/completionTokens/estimatedCost按 stageName 聚合，找 token 大户和成本高的模型调用，指导 Prompt 裁剪 / 模型替换
闭环：追踪数据 → 后台可视化 → 发现路由/检索/性能问题 → 调参（路由阈值、证据预算、rerank 策略、模型选择）→ 新一轮对话又落库 → 再看 benchmark 变化。stage_benchmark 的滑动窗口正是用来观测"调参前后 P50/P90 是否改善"的标尺。
