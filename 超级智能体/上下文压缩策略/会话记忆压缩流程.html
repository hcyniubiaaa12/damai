会话记忆的两种压缩哲学

总览 · 入口与分支

一个开关，两种命运

loadMemoryContext 先做空值与开关判断，再分流。两种模式产出的 ConversationMemoryContext 字段相同，但 assembledHistory 的构成与是否调用 LLM 截然不同。

滑动窗口

触发条件 · history-summary.enabled = false

只渲染最近 N 轮（rewrite-history-turns，默认 4）的原文，超出窗口的历史不持久化、直接丢弃。

  • 零 LLM 调用，纯字符串截断，极轻量
  • 近期保真：最近几轮一字不差
  • 远端失忆：旧话题一旦滑出窗口即不可见
  • longTermSummary 恒为空，compressionApplied = false

摘要压缩

触发条件 · history-summary.enabled = true（生产默认）

保留最近 K 轮（keep-recent-turns，默认 2）原文，溢出部分按批次压成结构化长期摘要并落库。

  • LLM 合并：旧摘要 JSON + 本批原文 → 新摘要，失败回退规则压缩
  • 长期记忆：旧话题以摘要形式保留，可回溯
  • 有成本：每次溢出触发模型调用，且状态需持久化
  • assembledHistory = 长期摘要 + 最近原文窗口
loadMemoryContext → conversationId 为空？ 是 → emptyContext() ｜否 → 读 historySummary.enabled → false：滑动窗口 ／ true：摘要压缩
流程图 A · 滑动窗口压缩

只留近端，旧的全丢

enabled = false 时走此分支。全程不碰 LLM、不碰摘要表，只做"取最近 N 轮 → 渲染原文 → 截断"三件事。

1入口：loadMemoryContextL92
传入 conversationId 与可选 traceRecorder（仅记录模型用量与检索链路，滑动窗口模式下几乎不参与）。
2空值短路L93–95
conversationId 为空 → 直接返回 emptyContext()，所有字段置零、compressionApplied=false。
3判定开关：enabled = falseL98
读 historySummary.enabled，为 false → 进入滑动窗口分支，跳过所有摘要逻辑。
4多取防漏：取最近 turns×3 条L100–101
按 rewrite-history-turns × 3（默认 4×3=12）从归档库拉取最近交换，多取是为过滤掉 RUNNING/空轮后仍够数。
5renderRecentTranscript：裁窗口L475–504
过滤掉 RUNNING 且无 Q/A 的轮次 → 只保留最后 N 轮（N=4）→ 每轮 Q 截 160 字、A 截 320 字 → 整体截到 recent-transcript-max-chars(2200)。超出窗口的历史在此被自然丢弃。
6renderAnswerRecentTranscript：只留问题L506–535
同样取最近 N 轮，但只保留用户问题（截到 answer-history-max-chars=1000），供问题改写/子问题拆分阶段使用，避免答案噪声。
7组装并返回L110–121
assembledHistory = recentTranscript；longTermSummary = ""；coveredExchangeId=0、compressionCount=0、compressionApplied=false。
压缩方式本质：不做任何"压缩"，只是截断。窗口之外的轮次既不入摘要表也不进上下文——它们对模型而言从未存在。代价低，但一旦话题回跳到旧轮，模型会"失忆"。

从溢出段切出至多 6 轮作为一个 batch，一次只推进一批，避免把超长历史一次性塞给模型。
6mergeSummaryPayload：LLM 合并L258–277
用 CONVERSATION_SUMMARY_MERGE 模板，把现有摘要 JSON + 本批原文交给模型，产出新的结构化摘要（summary / 目标 / 已确认事实 / 用户偏好 / 待跟进 / 检索提示），traceRecorder 记录用量。
LLM 失败 / 解析失败
6′fallbackMerge：规则回退压缩L276 / L288–314
降级路径：不调模型，用规则拼接——抽取"用户关注/已有结论"高亮、补充待跟进问题、正则提取检索词，裁剪到 summaryMaxChars。保证压缩永不为空。
7saveSummarySnapshot：落库前移水位L316–373
以本批最后一轮 exchangeId 为新 coveredExchangeId，coveredExchangeCount += batch，compressionCount++、summaryVersion++，写回 summaryText + summaryJson。并发保护：若库中水位已更高则跳过。
还有未处理批次 → 回到 5
8readSummaryPayload：解析摘要L128 / L384–398
优先解析 summaryJson 为结构化 payload；JSON 不可用时退回 summaryText 文本兜底。longTermSummary 取 summaryText。
9渲染最近 K 轮原文L130–143
按 recentFetchLimit(keepRecentTurns)（至少 K×3）取最近交换 → renderRecentTranscript 留最后 2 轮原文；同步 renderAnswerRecentTranscript 留问题供改写。
10assembleHistory：摘要 + 原文L148 / L550–552
assembledHistory = longTermSummary ＋ "\n\n" ＋ recentTranscript；compressionApplied = 摘要非空。返回 ConversationMemoryContext。
压缩方式本质：用 LLM 把旧对话"蒸馏"成结构化要点（带规则兜底），并分批增量推进——每批最多 6 轮、压完即落库前移水位，崩溃重跑只补未覆盖部分。代价是模型调用与状态管理，换来旧主题的可回溯性。
对比 · 一眼看穿差异

两条路的取舍

同样的输入对话，输出字段一致，但"成本 / 保真 / 记忆跨度"三角各占一端。

维度 滑动窗口（enabled=false） 摘要压缩（enabled=true）
压缩手段截断，只留最近 N 轮LLM 蒸馏 + 规则兜底，分批增量
旧对话去向丢弃，模型不可见折叠进长期摘要，可回溯
LLM 调用0 次每次溢出按批次调用，失败回退规则
持久化无额外存储摘要表（coveredExchangeId / version / count）
近期保真最近 N 轮一字不差最近 K 轮一字不差
长期记忆无，旧主题失忆有，目标/事实/偏好/待跟进结构化保留
assembledHistory= recentTranscript= longTermSummary + recentTranscript
compressionApplied恒为 false摘要非空时为 true
适用场景短会话、低成本、话题不回跳长会话、多主题切换、需长期连贯

一句话区分：滑动窗口是"近期复印、远期撕掉"，便宜但健忘；摘要压缩是"近期复印、远期誊写成摘要卡片"，费笔但记得久。当会话会反复回跳旧主题（如本例第 9 轮问回 T2），摘要压缩的价值才真正显现。
配置 · 驱动两种模式的关键旋钮

app.chat.rag 下的开关与阈值

均在 ChatRagProperties 与 application.yaml 中定义。下表为当前生产配置实值。

history-summary.enabled
true
总开关。false→滑动窗口；true→摘要压缩。生产默认开启。
rewrite-history-turns
4
滑动窗口保留的最近轮数（enabled=false 时生效）。
keep-recent-turns
2
摘要模式下始终保留为原文的最近轮数；溢出量 = stable − 此值。
compression-batch-turns
6
单次增量压缩最多推进的轮数，控制单次喂给模型的体量。
recent-transcript-max-chars
2200
最近原文窗口的字符上限，超出从头部截断。
summary-max-chars
1400
长期摘要文本的字符上限，LLM 与规则回退都会裁到此长度。
answer-history-max-chars
1000
问题改写专用历史（只含用户问题）的字符上限。
coveredExchangeId
动态
已摘要水位线（落库字段）。每批压缩后前移，崩溃重跑只补未覆盖部分。
