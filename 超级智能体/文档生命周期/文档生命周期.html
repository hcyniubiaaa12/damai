总览

文档从上传到最终可用，经历 3 大阶段、8 个子阶段。文档有三个独立的状态轴协同推进：

parseStatus WAIT_PARSE → PARSING → PARSE_SUCCESS → PARSE_FAILED
strategyStatus WAIT_RECOMMEND → RECOMMENDED → CONFIRMED → EXPIRED
indexStatus WAIT_BUILD → BUILDING → BUILD_SUCCESS → BUILD_FAILED
READY 状态： parseStatus=PARSE_SUCCESS(3) + strategyStatus=CONFIRMED(3) + indexStatus=BUILD_SUCCESS(3) 三者同时满足时，文档才可被检索。

结构节点提取 — 深度解析

从解析文本中提取章节结构树是整个文档生命周期的技术核心之一。以下从源码级别展开每个子阶段的设计细节和关键决策点，适合面试深度问答。

面试切入角度： 面试官可能会问"如果不依赖 LLM，如何从纯文本中判断一行是不是标题？""如何处理「1. 简介」这种既是列表又是标题的歧义行？""结构树构建完后如何保证父子关系正确？"—— 本节的每个组件都在回答这类问题。

// DocumentStructureNodeExtractor.java — 门面核心 public List<DocumentStructureNodeCandidate> extract(String documentTitle, String parsedText) { DocumentStructureSignalBatch signalBatch = signalExtractor.extract(title, text); List<DocumentStructureSignal> resolvedSignals = ambiguityResolver.resolve(title, allLines, rawSignals); List<DocumentStructureNodeDraft> drafts = hierarchyResolver.resolve(title, resolvedSignals); return treeValidator.validateAndBuild(title, drafts); }

阶段一：信号提取 — 正则优先级链

▼

DocumentStructureSignalExtractor 是整个系统最复杂的类（~615行），职责是将纯文本行分类为结构化信号。

逻辑行构建 — 原始行 → 逻辑行

解析文本（parsedText）不能直接用于信号分类，必须先转化为"逻辑行"列表。转换分两步：

第 1 步：按 \n 分原始行

String[] rawLines = parsedText.split("\n", -1); // 每一行得到: sourceLineNo（从1开始）、rawText

第 2 步：每行尝试内联拆分（splitInlineSegments）

不拆分的行（直接返回整行）：
# 标题 / |表格| / > 引用 / --- 分隔线
这些是完整的结构元素，从中间拆分会破坏语义。
触发拆分的行：
普通正文行包含 第X步 / 步骤X 模式时，在每步的边界位置切开。
目的是将一行里的多个步骤拆成独立逻辑行，每个单独识别为 STEP_ITEM。

每个逻辑行有 6 个属性：

属性含义示例
lineNo全局逻辑行号（从1自增，每个逻辑行一个）1, 2, 3...
sourceLineNo原始行号（追溯来自第几行）原始第1行 → 1
segmentIndex同一原始行内的片段序号1（没拆） / 1,2（拆了两段）
indentLevel缩进级别（空格数/4每tab）0 / 4 / 8
rawText原始文本（trim前）" 第一步：配置环境"
normalizedText规范化文本（trim后）"第一步：配置环境"

完整示例：

// 输入文本（3行） "# 简介第一步：配置环境 第二步：安装依赖" // 第0行: "# 简介" // → splitInlineSegments: 以#开头，不拆分 → 1个逻辑行 // → lineNo=1, sourceLineNo=1, segmentIndex=1, rawText="# 简介" // 第1行: "第一步：配置环境 第二步：安装依赖" // → splitInlineSegments: 非#/|/>，尝试拆"第X步" // → 找到2个边界 → 拆成2段 // → lineNo=2, sourceLineNo=2, segmentIndex=1, rawText="第一步：配置环境" // → lineNo=3, sourceLineNo=2, segmentIndex=2, rawText="第二步：安装依赖" // ↑ ↑ // lineNo各自递增 sourceLineNo都指向原始第2行 // 第2行: ""（空行） // → segments.isEmpty() → 直接加1条 // → lineNo=4, sourceLineNo=3, segmentIndex=1, rawText=""

关键设计 引入 sourceLineNo + segmentIndex 的目的是：内联拆分后仍可追溯原始行位置，用于上下文构建（buildContext() 时需要找前/后非空行）和日志调试。

分类优先级链（classify 方法）

对每个逻辑行，按以下优先级依次尝试匹配，一旦命中即返回：

优先级匹配模式输出 SignalKind置信度
1空行BLANK1.0
2重复噪声（高频页眉/页脚/版权）NOISE0.99
3页码（"第1页" / "Page 1" / "1/5"）NOISE0.98
4Markdown 标题 ^(#{1,6})\s+HEADING0.98
5明确步骤 "第一步/步骤1"STEP_ITEM0.96
6中文章节 "第三章 标题"HEADING0.96
7附录 "附录 A 说明"HEADING0.92
8多级数字 "1.2.3 标题"HEADING0.95
9表格行 |...|TABLE_ROW0.90
10引用 >QUOTE0.88
11复选框 [ ] / [x]LIST_ITEM0.92
12无序列表 - / * / +LIST_ITEM0.90
13单级数字 "1. 内容" 歧义点HEADING_CANDIDATE 或 LIST_ITEM0.62 / 0.93
14中文大纲 "一、内容" 歧义点HEADING_CANDIDATE 或 LIST_ITEM0.60 / 0.92
15普通正文 + 启发式判断HEADING_CANDIDATE 或 BODY0.58 / 1.0
歧义判定关键逻辑

单级数字（如 "1. 内容"）和中文大纲（如 "一、内容"）是最典型的歧义场景。系统通过三个维度综合判断：

1) 序号连续性检测（isNeighborSequence）： 检查当前行序号与前/后行是否构成连续整数序列。例如前一行是"1. 配置"，当前行是"2. 部署"→ 连续 → 判为 LIST_ITEM。

2) 引导句检测（previousIntroducesList）： 前一行是否以冒号（：:）结尾。例如"操作步骤如下："后跟"1. 打开配置"→ 判为 LIST_ITEM。

3) 标题启发式（looksLikePlainHeading）： 短文本（≤32字符）、无句号逗号、前后有空行隔离、下一行非分隔线 → 判为 HEADING_CANDIDATE。

算法要点 中文数字解析（parseLooseNumber）处理了"十一/二十/二十一/一百"等组合，支持 1-100 范围的中文数字转整数。

阶段二：LLM 歧义消除 — 规则兜底设计

▼

DocumentStructureAmbiguityResolver 对标记为 HEADING_CANDIDATE 的歧义行进行二次判别。关键设计点：

配置化阈值过滤
参数默认值含义
llmDisambiguationEnabledtrue总开关，可随时关闭退化为纯规则
ambiguityConfidenceFloor0.45置信度低于此值的信号直接忽略（太不可靠）
ambiguityConfidenceCeil0.80置信度高于此值的信号已是明确分类，无需 LLM
maxAmbiguousSignalsPerCall8单次 LLM 调用最多处理 8 个歧义点（Token 控制）
contextWindowLines2每个歧义点的上下文窗口行数
Prompt 构造策略

每个歧义点携带上下文窗口（含行号标记），LLM 决策线号 + 重定性结果：

// 生成的 Prompt 片段示例（简化） 文档标题：API 使用指南 第 1 个候选块（行号 15）： 13: 本章主要介绍认证流程 14: >> 15: 1. 认证方式 ← 歧义行，初始分类 HEADING_CANDIDATE 16: 支持 API Key 和 OAuth 两种方式 17: 认证方式的选择取决于应用场景 请判定：line 15 是 HEADING、LIST_ITEM 还是 BODY？
LLM 输出解析与合并

LLM 返回 JSON 数组，解析后按行号回填：

// LLM 返回示例 [ {"line_no": 15, "resolved_kind": "HEADING", "level_hint": 1}, {"line_no": 42, "resolved_kind": "LIST_ITEM", "level_hint": null} ] // applyResult() 合并到原始信号 → kind 更新为 HEADING, levelHint=1, confidence 提升至 max(原值, 0.88) → reasons 追加 "llm-disambiguated"
面试重点：回退机制 — 任何异常（LLM 超时/JSON解析失败/模型不可用）都通过 try-catch 静默回退到原始信号列表。系统不会因为 LLM 故障而中断整个提取流程。
catch (Exception exception) { log.warn("结构歧义判定失败，回退到规则结果"); return sourceSignals; }

LLM 设计原则 LLM 仅用于"规则无法确定的边界情况"（置信度 0.45~0.80），且单次调用不超过 8 个点。这控制了成本和延迟，也避免了 LLM 对明确行（置信度 > 0.80）的误判。

阶段三：层级树构建 — 状态机 + 栈

▼

DocumentStructureHierarchyResolver 将信号列表转换为草案节点树，核心是一个信号类型驱动的状态机。

状态机转移规则
信号类型动作状态更新
BLANK重置列表状态currentListItem=null, listStack.clear()
NOISE忽略无变化
BODY / TABLE_ROW / QUOTE追加到当前章节或列表项target.appendLine() — 内容累积
LIST_ITEM / STEP_ITEM解析列表父节点，创建列表节点，注册栈currentListItem=新节点
HEADING / HEADING_CANDIDATE创建章节节点，推导深度和父节点currentSection=新节点, listStack.clear()
深度推导策略（resolveHeadingDepth）

不同来源的标题用不同方式决定层级深度：

Markdown — 直接取 # 数量：
###### → depth=6
Chapter/Appendix — 强制 depth=1：
"第三章" → depth=1
Decimal — 通过 numericPath 找父节点推导：
"1.2.3" → parent=1.2 → depth=3
Plain/Ambiguous — 使用 context 推断：
前有空行→depth=1，否则 depth=2
列表嵌套栈

使用 Deque<ListContext>（双端队列作为栈）维护嵌套列表的缩进层级：

// 示例：缩进层级决定父子关系 1. 第一步 ← indent=0, parent=Section 1.1 子步骤 ← indent=4 > 0 → parent=上一步 1.2 另一个子步 ← indent=4 > 0 → parent=上一步 2. 第二步 ← indent=0, parent=Section (栈已清空) // resolveListParent: while (!listStack.isEmpty() && listStack.peekLast().indentLevel() >= indentLevel) listStack.removeLast(); // 弹出缩进大于等于当前行的项

设计要点 使用 latestHeadingByDepth 和 latestHeadingByNumericPath 两个缓存映射来快速确定标题的父节点。前者按深度索引最近标题（如 depth=1 最近章节作为 depth=2 的候选父级），后者按数字路径精确索引（如 "1.2" 精确查找父节点 "1"）。

各步骤详解
① collapseSyntheticTitleSection — 合并同标题章节。如果某个一级章节的标题与文档标题完全相同（无编码），将其子节点提升到根节点下，删除该冗余章节。
场景：Markdown 文件第一个 "# 文档标题" 与文档名重复时自动折叠。
② repairNumberedHierarchy — 按数字编号修复层级。对每个有 numericPath 的章节，根据路径查找精确父节点。
1.2.3 → 父节点是 1.2 → 父节点是 1
场景：PDF 解析时标题深度可能丢失（如所有标题都被赋 depth=1），但编号路径保留完整。
③ repairInvalidParents — 修复无效父节点。如果某个章节的父节点居然是一个列表项（isListLike），将父级上移。
场景：不规范文档中标题跟在列表项后面被错误分配父子关系。
④ recomputeDepths — 从根节点开始重新计算所有节点的 depth。根节点 depth=0，子节点 depth = parent.depth + 1。
场景：前两步修复可能改变了父子关系，深度必须重新计算保持一致。
⑤ rebuildPaths — 重建 canonicalPath（URL风格）和 sectionPath（人类可读，用 > 连接）。
canonicalPath: /document/1-2/system-overview
sectionPath: 第一章 > 系统概述
⑥ rebuildSiblingLinks — 按 lineNo 排序同级节点，设置 prevSiblingNodeNo 和 nextSiblingNodeNo。
场景：Neo4j 图投影需要 NEXT_SIBLING / PREV_SIBLING 关系来支持相邻章节查询。

设计原则 6 步修复按"先修复拓扑关系→再重建路径→最后补充辅助链接"的顺序执行。每一步都是确定性的纯函数，便于测试和排查问题。

为什么上传阶段要手动管理事务？

问题场景

上传操作做了三件事：写入 MinIO → 写入 MySQL (文档记录 + 任务记录) → 发送 Kafka 消息触发异步解析。

如果 Kafka 消息在事务提交之前就被消费者拉取，消费者读取到的文档状态可能还是旧数据；反过来如果 DB 写入失败但消息已经发出，就会产生幽灵消息（消息指向一个不存在的文档）。

源码实现：TransactionTemplate

上传方法没有用 @Transactional，而是用 TransactionTemplate 手动控制：

// DocumentManageServiceImpl.upload() // 不使用 @Transactional，而是： transactionTemplate.execute(status -> { // 1. insert document 记录 // 2. insert task 记录 // 3. insert task_log 记录 return null; }); // ⬆ 事务在此 commit，DB 连接释放 // Kafka 消息在事务提交后才发送 kafkaProducer.sendParseRoute(documentId, ...);

关键点： Kafka 发送在事务之外，确保消费者看到的 DB 状态一定是已提交的。如果事务回滚，根本不会走到发消息那行代码。

其它操作的声明式事务

确认策略 (confirmStrategy) 和触发索引构建 (buildIndex) 用的是 @Transactional(rollbackFor = Exception.class)，因为它们是单纯的 DB 写入操作，不需要协调外部消息中间件。

异步消费者 (handleParseRoute / handleIndexBuild) 没有事务，各 DB 操作用自动提交。因为 Kafka 消费者本身有 at-least-once 语义，配合幂等性设计即可。

同步 vs 异步 — 边界划分

整个文档处理链路中，Kafka 消息队列是唯一的异步边界。

同步（HTTP 线程）

  • 文件上传 — 用户直接等待结果，必须实时返回文档 ID
  • 策略查询 — 用户需要查看推荐策略后做决策
  • 策略确认/调整 — 用户交互决策点
  • 触发索引构建 — 仅校验 + 发消息，毫秒级
  • 删除文档 — 需要实时反馈结果
  • 特点：均为短平快操作，不在 HTTP 线程做重计算

异步（Kafka 消费者）

  • 内容解析 — Tika 解析大 PDF 可能数秒
  • 结构节点提取 — 可能触发 LLM 歧义消除
  • 文档画像生成 — 需要 LLM 调用
  • 策略推荐 — 基于完整分析结果的规则计算
  • 分块 + 向量化 + ES 索引 — 核心重计算
  • 特点：耗时 > 1s，需要解耦，可以失败重试
设计原则： HTTP 同步只做状态变更和消息分发，所有计算密集型任务全部异步化。Kafka 提供削峰填谷和失败重试能力。

父块-子块流水线策略 — 从源码到执行

文档切割不是一刀切，而是分层流水线：文档 → 父块（章节级回答单元）→ 子块（段落级检索单元），每层支持可插拔策略器，按策略步骤依次执行。

为什么需要父块 + 子块两层？

▼
仅子块的问题 检索结果不知道来自哪个章节；上下文碎片化无法回溯；无法实现按章节过滤；文档大纲无法重建。
父块 + 子块的好处 检索到子块可回溯父块作为上下文；支持按章节/父块范围过滤；父块携带文档元数据减少冗余；父子块可设不同的 chunk 参数。

buildParentBlocks() 内部执行 3 步：

Step 1: buildParentSeedList — 生成父块种子
// DocumentStrategyServiceImpl.java:217-240 private List<ChunkCandidate> buildParentSeedList(String parsedText, List<SuperAgentDocumentStrategyStep> parentSteps, List<SuperAgentDocumentStructureNode> structureNodes) { if (父块步骤包含 STRUCTURE && 结构节点存在) { // 1a. 按结构节点切分父块 List<ChunkCandidate> structureSeeds = buildStructureParentSeeds(structureNodes); if (structureSeeds 为空) return executePipeline(...) // 1b. 剩下的父块步骤（RECURSIVE）继续处理超长结构块 return executePipeline(structureSeeds, remainingSteps, PARENT); } // 2. 无结构 → 整段文本走 executePipeline return executePipeline([原始文本], parentSteps, PARENT); }

buildStructureParentSeeds 细节：

// 遍历所有结构节点，筛选出"有内容的章节节点" for (SuperAgentDocumentStructureNode node : structureNodes) { // 条件： // 1. nodeType == SECTION // 2. 该节点有内容（直接子节点不为空，或有 contentText） // 3. 跳过"仅作为容器"的中间节点（其子节点也是 SECTION） seeds.add(toChunkCandidate(node)); }

每个结构节点转成 ChunkCandidate 时，携带 sectionPath、canonicalPath、structureNodeId、itemIndex 等元数据，确保父块与原始结构节点关联。

Step 2: executePipeline — 流水线执行引擎
// DocumentStrategyServiceImpl.java:412-430 private List<ChunkCandidate> executePipeline(List<ChunkCandidate> sourceList, List<SuperAgentDocumentStrategyStep> orderedSteps, PipelineType type) { List<ChunkCandidate> currentChunks = sourceList; for (SuperAgentDocumentStrategyStep step : orderedSteps) { currentChunks = switch (step.getStrategyType()) { case STRUCTURE -> applyStructureChunking(currentChunks, type); case RECURSIVE -> applyRecursiveChunking(currentChunks, type); case SEMANTIC -> applySemanticChunking(currentChunks, type); case LLM -> applyLlmChunking(currentChunks, type); }; currentChunks = cleanupChunkList(currentChunks); // 过滤空块 } return currentChunks; }

流水线按步骤顺序依次执行，每步的输出是下一步的输入。每个策略器的职责：

策略器行为
applyStructureChunking当前块如果超过 maxChars，按结构节点边界切分；否则保持原样。
applyRecursiveChunking按 段落→行→句→滑动窗口 递归降级切分，直到每块 ≤ maxChars。
applySemanticChunking按 Jaccard 相似度聚类句子，合并语义相近的句子为块。
applyLlmChunking调用 ChatModel 智能判断切分点（默认关闭）。
Step 3: 子块切割 + 组装
// DocumentStrategyServiceImpl.java:192-213 for (ParentBlockCandidate parentSeed : parentSeedList) { // 对每个父块种子，调用 buildChildSeedList 生成子块 List<ChunkCandidate> childSeedList = buildChildSeedList(parentSeed, childSteps, structureNodes); // 如果子块列表为空，将父块本身作为唯一子块 List<ChunkCandidate> finalChildren = cleanupChunkList(childSeedList); if (finalChildren.isEmpty()) { finalChildren = List.of(cloneChunkCandidate(parentSeed, parentSeed.getText())); } parentBlockList.add(new ParentBlockCandidate( parentSeed.getSectionPath(), parentSeed.getStructureNodeId(), parentSeed.getStructureNodeType(), parentSeed.getCanonicalPath(), parentSeed.getItemIndex(), parentSeed.getText(), // 父块正文 parentSeed.getSourceType(), finalChildren // 子块列表 )); }

子块切割逻辑与父块类似，优先按 STRUCTURE 边界（如果有结构节点且父块绑定了 structureNodeId），再走其他策略降级。

无结构文档的 RECURSIVE 降级链路

当父块和子块都回退到 RECURSIVE 时，按以下优先级逐级尝试，直到切出的块不超过阈值：

paragraphs
→
lines
→
sentences
→
fixed window

每级切出的块如果 ≤ maxChars 则停止，否则降级到更细粒度再切。最坏情况下按固定窗口大小（maxChars - overlap）滑动截断。

关键参数 父块 maxChars=2200（硬编码），子块 maxChars=800（可配置于 app.manage.chunk.recursiveMaxChars）。

常见疑问：为什么只向量化子块，父块不向量化？

▼

常见疑问：为什么只向量化子块，父块不向量化？

Q1: 父块为什么不向量化？

这是 Parent-Child Retrieval 的标准设计：

// 子块（~800字符） → 向量化 → 检索命中层 // 职责：精准语义匹配，找到最相关的片段 // 粒度过大 → 语义模糊，一个向量无法代表整章内容 // 父块（~2200字符） → 不入向量库 → 上下文提供层 // 职责：命中子块后，通过 parent_block_id 回溯父块 // 用父块全文替换子块作为 LLM 上下文

如果父块也向量化：父块内容与子块高度重叠，向量几乎一样，检索时互相干扰；且父块粒度太粗，检索精度反而下降。成本和收益不成正比。

Q2: 父块不是标题吗，怎么有那么多文本？

父块不是标题节点，而是整个章节的内容聚合体。层级解析阶段通过 appendLine() 不断累加：

// HierarchyResolver 状态机：正文全部往 currentSection 追加 case HEADING → currentSection = 新章节节点 // 标题出现，切换当前章节 case BODY → currentSection.appendLine(line) // 正文追加到章节 case LIST_ITEM → currentSection.appendLine(...) // 列表项也追加到章节 // 最终 contentText 不是标题，而是整章内容： // "第一章：安装 // 安装方式有两种：在线安装和离线安装。 // 步骤1：下载安装包 // 步骤2：双击运行 // 步骤3：完成配置"

策略阶段 buildStructureParentSeeds 拿到的就是上面这一整块。所以父块能轻松到 2200 字符——它包含整个章节的正文、列表、步骤。

Q3: 命中子块后怎么获取父块上下文？

检索时子块元数据中携带 parent_block_id，提升阶段通过这个 ID 查数据库拿到父块内容：

// DocumentKnowledgeServiceImpl.elevateToParentBlocks() // 1. 从检索结果的 metadata 中提取 parent_block_id Long parentBlockId = childDocument.getMetadata().get(PARENT_BLOCK_ID); // 2. 按 parent_block_id 分组 childGroupsByParent.computeIfAbsent(parentBlockId, ...).add(childDocument); // 3. 批量查数据库拿父块 Map<Long, SuperAgentDocumentParentBlock> parentBlockMap = parentBlockMapper.selectList(in(parentBlockIds)); // 4. 用父块内容替换子块作为 LLM 上下文 elevatedDocuments.add(buildParentEvidenceDocument(parentBlock, childDocuments));

整个过程不走向量检索，就是一次 parentBlockMapper.selectList() 的数据库查询。子块负责"命中"，父块负责"提供上下文"——职责分离。
